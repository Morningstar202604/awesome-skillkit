# Migration Architect

Uses three tools to plan zero-downtime migrations, validate schema/API compatibility, and generate a rollback runbook — producing a phased plan, a compatibility report, and per-phase rollback steps.

## Input Checklist

| Input | Required | Description |
|---|---|---|
| Migration spec JSON | Yes | A spec file describing the migration; if none exists, copy and adapt from `assets/sample_database_migration.json` |
| Migration type | Yes | database / service / infrastructure (sets the compatibility check `--type`) |
| Before/after schema/API files | Required for compatibility checks | `--before` old, `--after` new JSON; samples in `assets/` |
| Output directory | No | Where the three artifacts are written; defaults to the current directory |

When inputs are missing, ask for all at once: "Please provide: (1) migration spec JSON path (if none, I'll draft one based on the assets sample and you confirm the migration content); (2) migration type (database/service/infrastructure); (3) the old/new schema file paths needed for the compatibility check."

## Pre-flight Checks

Run line by line; on any failure → fix per the remediation and STOP:

```bash
ls assets/sample_database_migration.json assets/database_schema_before.json assets/database_schema_after.json
# Expected: all three filenames. Missing → confirm repo integrity, then STOP.
```

## Workflow

Run commands inside the skill directory (`skills/programming/architecture/migration-architect/`).

### Step 1: Generate the migration plan

```bash
python3 scripts/migration_planner.py --input assets/sample_database_migration.json --format json -o migration_plan.json   # bundled sample spec; swap in migration_spec.json for your real scenario
```

- **Action**: generate a phased plan (`phases`), a risk list (`risks`), and an estimated duration (`estimated_duration_hours`) from the migration spec.
- **Expected**: `migration_plan.json` is generated and contains a non-empty `phases` array.
- **On failure**: rerun with `--validate` to check the spec structure; still failing → a spec field is missing; fix the fields against `assets/sample_database_migration.json` and retry.

### Step 2: Compatibility check

```bash
python3 scripts/compatibility_checker.py --before assets/database_schema_before.json --after assets/database_schema_compatible.json --type database --format json -o compatibility.json   # bundled sample (identical schemas → compatible rc=0); swap in database_schema_after.json to demo an incompatible report (rc=1 semantics)
```

- **Action**: compare before/after schemas/APIs (`--type database|api`), and output `overall_compatibility` plus `breaking_changes_count` / `potentially_breaking_count`.
- **Expected**: exit code 0 and `overall_compatibility: compatible`.
- **On failure**: not compatible → list each breaking/potentially-breaking item for the user to decide: fix the schema and rerun, or the owner explicitly accepts it in writing. **Gate:** the migration isn't approved until one of the two is met.

### Step 3: Generate the rollback runbook

```bash
python3 scripts/rollback_generator.py --input assets/sample_migration_plan.json --format both -o rollback_runbook   # bundled sample plan (generated by migration_planner on the sample spec)
```

- **Action**: generate a rollback runbook from the Step 1 plan (both json and text formats).
- **Expected**: `rollback_runbook.json` and `rollback_runbook.txt` are generated; the runbook covers every phase in the plan.
- **On failure**: an error like "input file missing phases" → the Step 1 artifact is corrupt; rerun Step 1.

### Step 4: Delivery and pre-execution gate

- **Action**: deliver the three artifacts, and check off the pre-execution gate item by item: (1) compatibility passes (Step 2); (2) every phase has a rollback runbook (Step 3); (3) rollback steps have been rehearsed on staging; (4) monitoring and alerting are in place.
- **Expected**: all four gate items satisfied; declare explicitly to the user "the plan is ready; the migration has not yet been executed" (this skill only produces plans and scripts; it doesn't run the migration).
- **On failure**: any gate item unmet → list the gaps, STOP; after a schema revision, rerun all checks from Step 1.

## Parameter Cheat Sheet

| Parameter | Values | Description |
|---|---|---|
| `--input, -i` | JSON file | migration_planner reads the migration spec; rollback_generator reads the migration plan |
| `--before / --after` | JSON files | compatibility_checker's old/new version files |
| `--type` | database / api | The type of object under compatibility check |
| `--format` | json / text / both | Common to all three scripts |
| `--output, -o` | file-path prefix | Where artifacts are written |
| `--validate` | boolean | migration_planner validates the spec structure |

## Failure Handling Table

| Symptom / error code | Cause | Fix |
|---|---|---|
| compatibility non-zero exit | Breaking changes detected | Hand to the user to decide: fix the schema and rerun, or accept in writing; don't silently pass |
| The rollback runbook misses a phase | The Step 1 plan artifact is corrupt | Rerun Step 1, then regenerate the runbook |
| `--validate` errors | Missing migration-spec fields | Fill fields in one by one against `assets/sample_database_migration.json` |
| `FileNotFoundError` | Not running in the skill directory | `cd` to the skill directory or use absolute script paths |

## Migration Pattern Quick Reference (for selection)

| Scenario | Pattern | Key actions |
|---|---|---|
| Adding a column/table | Expand-Contract | Add the new structure → dual-write → backfill → verify, then drop the old structure |
| Zero-downtime on a large dataset | CDC / Incremental Sync | Stream-capture changes into the target DB; eventual consistency |
| Replacing a service | Strangler Fig | Gateway traffic-splitting → incremental implementation of the new service → retire the old component |
| Validating old vs new in parallel | Parallel Run | Dual execution + result comparison → cut over by confidence |
| Gradual rollout | Canary | Start with small traffic → watch latency/error rate/KPIs → ramp in stages |
| Auto-fallback when the new system degrades | Circuit Breaker | Fall back to the old system on failures over a threshold; half-open probes for recovery |

See the reference files for detailed explanations and data reconciliation (row-count checks, checksums, delta SQL).

## Delivery Criteria

- Definition of success: `migration_plan.json` (with non-empty `phases`/`risks`), `compatibility.json` (`overall_compatibility` is compatible, or breaking items are accepted in writing), and `rollback_runbook.json` + `.txt` (covering all phases) are all present, and the four pre-execution gates are met.
- Artifact naming: `migration_plan.json`, `compatibility.json`, `rollback_runbook.{json,txt}` (or a user-specified prefix).
- Save location: current directory or a user-specified directory.
- Completeness verification: all three JSON files parse with `json.load`; the plan's phase list maps 1:1 to the phases the runbook covers.
