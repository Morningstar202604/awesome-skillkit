# Dependency Auditor

Offline, deterministic dependency audit across 8+ package ecosystems. The three scripts only pattern-match manifests/lockfiles — they do **not** call online vulnerability-advisory APIs; pair their findings with `npm audit` / `pip-audit` / `cargo audit` to cover the latest CVEs.

---

## Input Checklist

| Input | Required | Description |
|------|------|------|
| Project path | Yes | Repo root, or a directory containing manifests/lockfiles. |
| Output format | No | `json` (default for the script scenarios) or `text`. |
| Failure threshold | No | `--fail-on-high` makes the scanner exit non-zero when a high-level finding appears. |
| Risk threshold (planner) | No | `low` \| `medium` \| `high` (default `medium`). |
| Time window (planner) | No | Day window for the upgrade plan (default `90`). |

When the project path is missing, ask only once:

> Please provide: (1) the project path (the directory containing package.json / requirements.txt / go.mod, etc.).
> I'll use the rest as defaults: format=json, risk-threshold=medium, timeline=90 days.

## Pre-flight Checks

```bash
# 1. Are the scripts complete?
test -f scripts/dep_scanner.py && test -f scripts/license_checker.py \
  && test -f scripts/upgrade_planner.py && echo "scripts-ok" \
  || { echo "ERROR: scripts/ missing — bundle incomplete"; exit 1; }

# 2. Is Python available?
command -v python3 >/dev/null 2>&1 || { echo "ERROR: python3 not found"; exit 1; }

# 3. Is there a recognizable manifest in the target directory?
ls "$PROJECT"/*.json "$PROJECT"/go.mod "$PROJECT"/Cargo.toml \
  "$PROJECT"/Gemfile "$PROJECT"/pom.xml "$PROJECT"/composer.json 2>/dev/null \
  | grep -q . || { echo "WARN: no known manifest found in $PROJECT"; }
```

## Workflow

### Step 1: Scan for vulnerabilities

```bash
python3 scripts/dep_scanner.py examples/sample-project --format json --fail-on-high -o scan.json   # bundled sample project; swap in your real project root
```

Expected: `scan.json` contains per-package findings; with `--fail-on-high`, a single `high` finding exits non-zero. On failure: when no manifest is found the scanner reports 0 findings — rerun with the correct project path.

### Step 2: Check license compliance

```bash
python3 scripts/license_checker.py examples/sample-project --policy permissive --format json -o licenses.json   # the offline sample has no license metadata; the strict gate (exit code 1 when score<80) is left for your real project
```

Expected: `licenses.json` lists license classifications and conflict pairs (e.g. GPL mixed into a permissive project). On failure: `--policy strict` flags unknown licenses for human review — treat them as conflicts until verified.

### Step 3: Plan upgrades

```bash
python3 scripts/upgrade_planner.py examples/scan.json --risk-threshold medium --timeline 90 --format json -o plan.json   # bundled sample scan result (generated by dep_scanner on the sample project)
```

Expected: `plan.json` lists upgrade items sorted by risk, each with rollback instructions. `--quick-scan` skips transitive dependencies; `--security-only` limits the plan to security fixes. On failure: the planner depends on Step 1's `scan.json` — confirm the file exists.

### Verification loop

After applying upgrades, rerun Step 1 and assert **0 high-level findings** before closing this audit.

## License Classification

- **Permissive**: MIT, Apache 2.0, BSD (2/3-clause), ISC
- **Strong copyleft**: GPL v2/v3, AGPL v3 — flagged as contamination risk in permissive projects
- **Weak copyleft**: LGPL v2.1/v3, MPL 2.0
- **Proprietary / dual-licensed / unknown** — unknown licenses surface for human review

The checker analyzes license inheritance along the dependency chain and outputs conflict pairs plus remediation suggestions.

## Upgrade Risk Matrix

| Risk | Update type | Action |
|---|---|---|
| Low | Patch, security fix | Apply immediately |
| Medium | Minor with new features | Fold into the routine update batch |
| High | Major version, API change | A separate migration task + add tests |
| Critical | Known breaking change | Scheduled migration with a rollback process |

Priority: security patches > bug fixes > feature updates > large rewrites.

## Scripts (honest capability statement)

- **`scripts/dep_scanner.py`** — multi-format parser; built-in offline vulnerability pattern set (~16 CVE patterns — a smoke layer, no substitute for online advisories); parses transitive dependencies from lockfiles; JSON + text output.
- **`scripts/license_checker.py`** — detects licenses from package metadata; a compatibility matrix covering 20+ license types; `--policy permissive|strict`; conflict detection with remediation suggestions.
- **`scripts/upgrade_planner.py`** — predicts breaking changes from semver; outputs a risk-sorted migration plan with a test checklist and time estimates.

Sample fixtures: `test-project/` and `test-inventory.json` in this directory; expected output shapes are in `expected_outputs/`.

## Failure Handling Table

| Symptom | Cause | Action |
|------|------|------|
| Reports 0 findings despite clear dependencies | Wrong project path | Rerun from the directory containing the manifests |
| `high` finding blocks CI | Expected behavior of `--fail-on-high` | Triage scan.json; patch/pin before merge |
| Unknown-license conflict | SPDX id not recognized | After human verification, whitelist it with a written rationale |
| Planner reports missing input | `scan.json` doesn't exist | Run Step 1 first |

## Delivery Criteria

Success = the three artifacts are present and reconciled against each other:

- `scan.json` — findings decide which packages to pin/patch now.
- `licenses.json` — conflicts handed to the user as a legal-risk list.
- `plan.json` — a risk-sorted upgrade plan with rollback instructions.

Verification: after upgrading, rerun Step 1 and confirm 0 high-level findings. Artifacts go in the project's `audit/` or a CI artifact directory. This skill only audits — it never rewrites the user's manifest files.
