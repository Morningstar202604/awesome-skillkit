# PRD 撰写指南

本 skill 是 product-prd-writer 的工作手册。核心原则：**需求写清楚"做什么、为什么、怎么算做完"，不写"怎么做"**。一份合格 PRD 让开发能实现、QA 能验收、设计能补稿，不留"开发时再定"的黑洞。

## 这是什么

一套从模糊需求到可交付 PRD 的撰写流程。每个功能点必须包含：用户故事（As a / I want / So that）、业务规则、正常流与异常流、验收标准（Given-When-Then）、埋点需求。文档长度按功能复杂度，不堆砌套话。

## 何时使用

- product-prd-writer 接到"写 PRD/补需求文档"任务时，必须加载本 skill。
- product-manager 整合跨职能需求、对齐版本目标时，参考本指南校验完整性。
- product-qa 评审需求可测性时，用本指南核对验收标准是否可判定。
- product-qa-reviewer 终检时，按本指南章节逐项核对缺漏。

## 核心步骤

1. **写背景与目标**：一句话业务背景、要解决的用户问题、成功指标（对应 `product-metrics-guide`），不超过 300 字。
2. **列用户故事**：按角色拆分，每条格式"作为<角色>，我希望<动作>，以便<价值>"，标注优先级 P0/P1/P2。
3. **画流程与规则**：主流程图（文本版）、业务规则清单（如"满 99 免运费"）、权限与状态机。
4. **写边界与异常流**：空态、加载中、失败/超时、无权限、网络断、并发冲突——每个异常给预期表现。
5. **写验收标准**：每条功能用 Given-When-Then 至少 1 条正例 + 1 条反例，可被 QA 直接转用例。
6. **补埋点与非功能**：需要采集的事件名/属性、性能阈值（如首屏 <2s）、兼容与合规要求。
7. **标依赖与不做**：列出依赖项与本期明确"不做"的范围，防止需求蔓延。

## 清单

- [ ] 背景/目标/成功指标写了，且指标可量化。
- [ ] 用户故事按角色拆分，每条带 P0/P1/P2。
- [ ] 主流程与业务规则列清楚，无歧义。
- [ ] 空态/加载/失败/无权限/断网异常流都覆盖了。
- [ ] 验收标准用 Given-When-Then，正例反例都有。
- [ ] 埋点事件名与属性列了。
- [ ] 性能/兼容/合规等非功能需求写了。
- [ ] 依赖项与"本期不做"范围明确。
- [ ] 全文无"开发时再定""视情况"等黑洞措辞。

## 易错点

- **只写 happy path**：漏了失败/空态/权限分支，开发和 QA 各猜各的，上线后出边界 bug。
- **验收标准不可判定**：写"体验要好""响应快"，QA 无法转用例。必须写成可观察、可测量。
- **需求蔓延**：把"以后可能要"也塞进本期，没有"不做"清单。
- **缺埋点定义**：上线后不知道功能有没有人用、漏斗在哪一步掉。
- **业务规则分散**：规则散落在正文各处，没有集中清单，开发漏看一条就错。
