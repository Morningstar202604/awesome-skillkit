# 编排协议（Orchestration Protocol）

所有 team-lead 的共享编排纪律。本文件是**提炼**，不是新规则：它把 18 支团队 lead 正文中
已有的门禁、回炉、断路、交接、技能回退实践收敛为一份最小公约数，供跨团队一致遵守。

lead 必须在正文中引用本文件（由 `verify.py` 第 7 节强制检查）。

## 分层声明

| 层 | 含义 | 本协议条目 |
|----|------|-----------|
| **L1 可强制** | 由 `verify.py` 或宿主能力机械执行，不依赖模型自觉 | §0 引用、成员登记、路由有效性、只读 `tools` 约束 |
| **L2 建议** | prompt 层约定，依赖模型遵守；宿主无法机械验证 | §1-§6 全部编排纪律 |

L2 条目是**行为建议**而非硬保证：宿主若需硬保证（如 git tag 检查点），须自带 bash/git
能力并在 agent prompt 中声明；无该能力的宿主按「尽力而为」执行，不视为违约。

## §0 引用义务（L1）

- 每个 `*-team-lead.md` 正文必须出现 `orchestration-protocol.md`。
- 新增团队时同步 `project-director.md` 路由、`TEAM.md` 成员表、`verify.py` 的
  `EXPECTED_TEAM_AGENTS`（三处缺一即门禁红灯）。

## §1 质量门禁（L2）

- 关键交付前必过门禁：`accuracy-and-fact-check`（事实核查，防幻觉）+
  `quality-gate-checklist`（7 维质检），或团队内等价只读质检角色。
- **H 级（critical）问题不交付**；H 未清零不得进入汇编/上线/提交。
- 质检角色只读：出问题清单与结论，不改交付物；改由实现方整改后重审。

## §2 回炉上限（L2）

- 同一产出被驳回 **≤ 2 次**后停止重复派单：第 3 次先重查目标 / brief / 输入假设，
  确认无误再重派。
- 重复派单前必须变更输入（换视角、拆粒度、换成员），不允许原样重试。

## §3 断路与切换（L2，模板见 fullstack-team-lead）

- 触发阈值（按对话轮次计）：阶段产出 3 次不合格 / 成员 2 次死循环 / 1 次卡死。
- 切换优先级：① 换成员 → ② 降级裁剪（如完整流程→最小可行流程）→ ③ 拆小重派
  → ④ 回滚到稳定检查点（仅宿主具备 git 能力时）→ ⑤ **请用户决策（优先级最高，
  触发即停其余切换）**。
- 同一方案无脑重试上限 3 次，之后强制升级用户介入。
- 无第二成员可换的单人环节：跳过 ①，直接 ②③④⑤，不得硬撑。

## §4 交接块（L2）

每次派单给成员必须携带四块，缺块即视为无效派单：

1. **目标**：这次要产出什么、验收标准；
2. **输入**：上游完整产出原文（参考成员 `## 输入规范` 与 `## 交接模板`）；
3. **约束**：风险分级结论、口径/合规要求、不可动的边界；
4. **输出格式**：交付物结构与汇报格式。

## §5 阶段汇报与上下文纪律（L2）

- 每阶段结束用 **3 行以内**汇报：完成项、卡点、下一步。
- 长链路做增量摘要：保留关键结论 + 遗留风险 + 决策记录，丢弃过程细节；
  传给下一成员的仍是**完整产出原文**，lead 自身上下文只留摘要。

## §6 技能回退（L2）

- 开工先扫团队 skills，命中即按其框架执行；lead 指定 skill 以它为准。
- skill 调用失败 / 未安装 → 退回通用经验，**不阻塞交付**。

## 风险分级速查（L2）

按「发生概率 × 影响程度」定级：阻断×高 = **H**（不交付）、降级×中 = **M**（整改后交付）、
可忽略×低 = **L**（记录即可）。无依据不得判级；事实存疑先走 §1 核查。
