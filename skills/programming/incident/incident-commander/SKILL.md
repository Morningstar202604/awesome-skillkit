# Incident Commander

A command-and-post-mortem framework for availability/reliability incidents: severity classification, timeline reconstruction, and structured post-incident review (PIR). This skill handles orchestration and decision-making; it does **not perform the remediation actions it assigns**.

> Distinction: this skill handles availability incidents (outages, degradation, failed releases). Security incidents (ransomware, intrusion, data exfiltration, IOC forensics) → route to `incident-response`. Both use SEV1–SEV4, but this skill classifies by business impact (users/revenue/SLA).

## Input Checklist

| Input | Required | Description |
|------|------|------|
| Incident description / symptoms | Required | Free text or JSON (affected-user ratio, business-impact level) |
| Timeline event source | Conditionally required | When generating a timeline: `--input` event JSON |
| Incident data file | Conditionally required | When generating a PIR: `--incident` data JSON + `--timeline` markdown |
| Output path | Optional | `--output` filename; otherwise stdout |
| RCA method | Optional | `--rca-method`: `5whys`/`fishbone`/`timeline` (default per the script) |

When inputs are missing, ask for all at once: "Please provide: (1) incident description (affected-user ratio + business impact high/medium/low), (2) whether to reconstruct a timeline (needs event JSON), (3) whether to generate a PIR (needs incident data + timeline), (4) output filename. Everything else runs on defaults."

## Workflow

### Step 1: Severity classification (SEV)

```bash
python3 scripts/incident_classifier.py --input assets/simple_incident.json --format text   # bundled sample event; swap in your real incident.json
# Pipe usage: echo '{"description": "…", "affected_users": "80%", "business_impact": "high"}' | python3 scripts/incident_classifier.py
```

Expected: the script outputs the SEV level and the recommended response team / initial actions.
On failure: the input lacks `affected_users`/`business_impact` → fill in the fields or use free text with `--format text`; a JSON parse error → check the field names.

Severity quick reference (full version in `references/incident_severity_matrix.md`):

| Level | Definition | Commander on site | External comms |
|------|------|---------|---------|
| SEV1 | All users / critical business unavailable, data loss | ≤5 min | ≤15 min |
| SEV2 | >25% of users clearly degraded | ≤30 min | ≤30 min |
| SEV3 | Localized, with a temporary workaround | ≤2 h (business hours) | At milestones |
| SEV4 | Cosmetic / documentation / monitoring gap | 1–2 business days | None needed |

### Step 2: Reconstruct the timeline

```bash
python3 scripts/timeline_reconstructor.py --input assets/sample_timeline_events.json --output timeline.md
python3 scripts/timeline_reconstructor.py --input assets/simple_timeline_events.json --detect-phases --gap-analysis
```

Expected: a time-ordered event narrative with phase detection and gap analysis; written to a file with `--output`.
On failure: the event-source JSON is malformed → validate the schema against `assets/sample_timeline_events.json`.

### Step 3: Generate the PIR (post-mortem)

```bash
python3 scripts/pir_generator.py --incident assets/sample_incident_pir_data.json --timeline assets/sample_timeline.md --output pir.md   # bundled sample (timeline.md was generated by the reconstructor above on the sample events)
python3 scripts/pir_generator.py --incident assets/sample_incident_pir_data.json --rca-method fishbone --action-items
```

Expected: a structured PIR with an RCA (per the chosen method) and trackable follow-up action items.
On failure: missing `--timeline` → run Step 2 first; an invalid `--rca-method` → use one of `5whys`/`fishbone`/`timeline`.

## Communication Cadence

Determine the update frequency by stakeholders and severity (full matrix in `references/sla-management-guide.md`):

| Stakeholder | SEV1 | SEV2 | SEV3 |
|--------|------|------|------|
| Engineering lead | Real-time | 30 min | 4 h |
| Executives | 15 min | 1 h | Same day |
| Customers | 15 min | 1 h | Optional |

Initial communication template structure (full templates in `references/communication_templates.md`):

```text
Subject: [SEV{severity}] {Service Name} - {Brief Description}
Incident Details: Start Time / Severity / Impact / Current Status
Affected Services / Symptoms / Initial Assessment
Incident Commander / Technical Lead / SMEs
Next Update / Status Page / War Room
```

## Parameter Cheat Sheet

| Parameter | Values | Description |
|------|------|------|
| `--format` | `text`/`json` | Classifier output shape |
| `--input` | JSON path | Timeline event source |
| `--output` | file path | Where to write the timeline/PIR |
| `--detect-phases` / `--gap-analysis` | flag | Timeline phase and gap analysis |
| `--incident` | JSON path | Incident data for the PIR |
| `--timeline` | md path | Timeline input for the PIR |
| `--rca-method` | `5whys`/`fishbone`/`timeline` | RCA framework |

## Failure Handling Table

| Symptom / error code | Cause | Fix |
|------------|------|------|
| Classifier JSON parse failure | Missing/malformed fields | Fill in `affected_users`/`business_impact` or use `--format text` |
| Timeline `--input` malformed | Schema mismatch | Compare against `assets/sample_timeline_events.json` |
| PIR missing `--timeline` | Timeline not built first | Run Step 2 first |
| Invalid `--rca-method` | Typo | Use one of the three valid values |

## Delivery Criteria

Definition of success: produce an SEV classification + timeline md + PIR md (with RCA and action items), and the action items have owners and due dates.
Artifact naming: `timeline.md`, `pir.md` (or user-specified names).
Save location: incident tracking system / version control; share the PIR widely.
Completeness verification: every action item in the PIR is trackable; the timeline covers detection→mitigation→recovery end to end; the classification matches `incident_severity_matrix.md`.

## Safety Red Lines

- **This skill only orchestrates; it does not remediate**: never execute the mitigation/rollback commands it assigns. Actual remediation (rollback, scaling, config changes) is performed by the on-call engineer in the war room, with user confirmation.
- Prefer disabling via feature flag over code rollback; roll back the database only for non-breaking migrations (forward migrations preferred).
- Hold a blameless post-mortem culture: focus on system failure, not individual error.
