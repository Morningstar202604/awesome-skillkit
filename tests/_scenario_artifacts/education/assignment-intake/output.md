## Assignment Intake Analysis

### ⚠️ Critical Blockers (必填项缺失)

在解析之前，必须指出原文本中**完全缺失**的三项核心信息，这会导致下游 `solution-drafter` 无法开工。请在最终 JSON 的 `notes` 或单独清单中标记：

1.  **年级与学科**：未知（"操作系统课程设计"常见于计算机科学与技术本科大二/大三，但也可能出现在高职或高中信奥拓展课，**学段决定评分深度与技术栈预期**）。
2.  **作业原文完整性**：该描述极大概率为**口述转写**或**聊天记录片段**，缺失关键硬性约束（如：编程语言、交付物形式、字数/页数、截止时间、是否需源码、是否有参考模板）。
3.  **具体进度/约束**：是"从零开发"还是"修改现有内核"？是模拟环境还是真实硬件？

### 1. 题型识别 (Type Identification)

*   **判定逻辑**：
    *   包含"课程设计"关键词 → 指向 **lab_report (实验报告)** 或 **essay (技术论文)** 的混合体。
    *   包含"操作系统的...进程" → 强技术实践属性，非纯理论作文。
    *   包含"做" → 有产出物要求（代码+文档）。
*   **结论**：`type: lab_report` (主) + `secondary: essay` (如需撰写设计说明书)。
    *   *注：若最终仅需提交PPT答辩，则转为 `slides`，但通常OS课程设计隐含代码交付。此处按标准 lab_report 处理。*

### 3. 评分点映射 (Scoring Points)

基于 `lab_report` 默认维度 + OS课程特殊要求：

1.  **功能正确性**：进程调度/同步等核心逻辑运行无误（可验证）。
2.  **技术深度**：对OS内核机制（如PCB结构、调度算法、锁机制）理解准确。
3.  **创新性体现**：明确标注"新意"所在（如：实现了非抢占式调度、设计了新的调度策略、优化了上下文切换效率、提供了更好的调试可视化）。
4.  **报告规范性**：设计文档结构完整（目的、原理、实现、测试、反思）。
5.  **代码质量**：注释清晰、模块化、无内存泄漏（若要求源码）。

### 4. 真实素材清单 (Needed Materials)

| 素材 (material) | 原因 (why) | 提供方式 (how_to_provide) |
| :--- | :--- | :--- |
| **课程大纲/任务书全文** | 当前描述过于含糊，缺失评分权重、技术栈限制、参考资源列表。 | 请用户搜索课程群通知或教材附录，粘贴完整任务描述。 |
| **指定编程语言/框架** | "OS课程设计"各校差异巨大（有的用C写简易OS，有的用Python模拟）。 | 确认：是否必须用C？是否提供内核源码骨架？ |
| **已有基础/前置知识** | 判断"新意"的基准线：是初学者创新还是进阶创新？ | 用户自述：是否学过《操作系统概念》？是否做过之前的小作业？ |
| **具体"新意"方向偏好** | "有点新意"太宽泛，需学生提供兴趣点（如：想做实时调度？想做图形化界面？）。 | 用户口述一个感兴趣的方向，或列出2-3个候选想法。 |
| **截止时间** | 规划开发节奏。 | 提供具体日期。 |
